# Current decisions

## Working agreement

**warn** the user before decisions that can cause path, state, or calculation explosions — branches, loops, numeric expressions, fixed points, widening — before major architecture or file-structure changes, and before important data-structure decisions become difficult to reverse.

Prefer correctness by construction over correctness by review: when a rule must hold across many places (every numeric arm stamps blame, every write form demotes a binding, every producer keeps an interval invariant), reshape the code so one place enforces it and forgetting is impossible, rather than repeating the pattern and relying on adversarial reviews to catch the missed spot. Reviews stay as the safety net, not the mechanism.

Soundness reviews aim at code people actually write. A hole reachable from ordinary code — a value that can become NaN, a stale constant published after a plain reassignment — deserves a real fix. A hole that needs contrived code, e.g. an `eval` string reassigning a module binding, or a property named `eval`, is still worth reporting, but the response is to move the construct out of the accepted subset (next section) or make it claim-free by construction (the `as unknown` erasure), not to handle the corner cleverly. Review prompts should say so, or the reviewers drift into hunting exotic spellings as if they were security exploits.

## What TypeScript code does the analyzer accept?

Acceptance is decided early, in one place, against a written list — not discovered piecemeal as lowering trips over constructs. A function using anything outside the list is rejected before analysis and reported as unsupported with the construct and its location; the file's other functions are unaffected, and the module initializer skips the statement and keeps going (see the partial-results section). This is built: `src/lower/accept.ts` runs once per function declaration and once per top-level initializer statement, before any lowering, and hosts the wholesale rules below. Unknown syntax stays rejected by default through lowering's catch-all arms, and a few checks remain at the positions they describe (parameter and return types, branch conditions, mixed-kind declarators); every rejection flows through the same tagged reasons either way.

The analyzer's guarantees are built on the TypeScript checker's word — parameter types, declared types, return types. So the subset excludes exactly the code where that word is void:

- `any`-typed values are carried claim-free, like `unknown`: the checker's word is void for them, so the analysis says nothing about them either — every operation on one stops at a gate, a write of one into a typed binding leaves the binding claim-free instead of letting the declared type restore claims, and the declared-kind assumes lines (which exist precisely because TypeScript lets `any` flow into any write position) cover the reads that rest on them. Rejecting `any` wholesale was the earlier rule; carrying it keeps the surrounding numeric code analyzable, e.g. a function that logs an `any`-typed payload but computes its return from numbers.
- Type assertions written with `as` or angle brackets erase to a claim-free opaque — the function around a cast analyzes, and only the paths that use the erased value stop, honestly. An assertion is exactly where the checker's word and the runtime value may diverge, and three review rounds settled that no type-level carry license survives: erasing only `as unknown`/`as any` was defeated by the comparability route `true as {} as number`; a top-level kind match was defeated one structural level down by `flags as unknown[] as number[]`; the recursive type-shape comparison was defeated through its optional-property skip and its heterogeneous-union fallback. Each attack was diagnostic-clean TypeScript reaching a `Cannot join` crash. The one exception stays `as const`, which TypeScript permits only on literals and which narrows a literal to its own literal type — the value kind provably cannot change. The non-null assertion `x!` stays accepted where it does not change the value kind, with one blessed kind-changing form: `array[index]!`. The syntax itself requests asserted-read treatment: an unproven read adds an assumption line (`assumes: the element read at <site> is in bounds`), a read a loop proves — the for-of counter — adds nothing, and an asserted read on a provably empty array stops the path. A bare read carries possible undefined regardless of the project's `noUncheckedIndexedAccess` setting.
- `var`. Hoisting gives one variable several declaration sites and lets a nested redeclaration write a binding declared elsewhere, e.g. `var x = 1; { var x = 2 }` is one variable. `let` and `const` express the same programs without that. Rejected; `var` names never become module bindings, so a function reading one is rejected as an unknown identifier.
- `eval`. A file-wide rejection: an eval string can rewrite bindings that every function's report depends on, so rejecting only the function containing the call would not protect the others. Any mention of the identifier `eval` anywhere in the file puts every function outside the subset and stops the initializer. The detection is a plain identifier scan, deliberately over-rejecting — every spelling that can reach module scope, e.g. `(eval)(...)`, contains the identifier, so no call-shape or wrapper detection is needed. (A known cost: a property named `eval`, e.g. a chess engine's `position.eval`, rejects the file too.)
- Assignments used as values inside larger expressions, e.g. `cond ? (x = 1) : 2` or `a = b = 5`. Assignments lower only in statement position (their own statement, or a for-loop incrementor) — code-golf value-position writes are the one shape nobody writes, and rejecting them makes ternary and logical-operator arms provably assignment-free, so their join carries exactly one value and needs no binding merge. Statement-level `if`/`else` assignment to a `let` stays fully supported: multi-statement branches computing intermediates are ordinary code, and loops need the same binding-merge machinery regardless.
- Type-check suppression comments: `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`. The other file-wide rejection. The directive turns off the checker somewhere in the file, and every guarantee rests on the checker's word — `// @ts-expect-error` above `let width: number = true` puts a boolean where every number invariant applies, with no `any` in sight. Detection is a full-text scan, again deliberately over-rejecting (the directive could sit inside a string).

What is accepted today, stated positively: functions whose values are numbers, booleans, strings (carried without claims: string literals, template strings, and `===` dispatch on them analyze, and no numeric fact is ever stated about one), records mixing those (single-kind unions like `1 | 2` included, optional properties read as maybe-undefined), records whose types the project did not write (declared only in .d.ts files — DOM elements, library interfaces) carried as opaque leaves rather than contracted, and any property the classification cannot walk (a recursive route, a mixed-literal union) likewise carried without claims instead of vetoing its record; intersections of object types (`Base & {subPage: 'select'}`) as merged records, including as tagged-union variants; tagged unions of record shapes (`{type: 'lightbox'; index: number} | {type: 'archive'; page: number}` — the value carries one record per variant, `route.type === 'lightbox'`, `switch (route.type)`, and `'tab' in route` all narrow the variant list per branch, literals remember which variant they build, two variants may share a tag value, and a nullable wrapper carries the union like any inner; the representation mirrors the declared type's tree, so it is bounded by what the author wrote and analysis only ever removes variants), `number | null` / `number | undefined`, arrays, and `as const` tuples; parameters take any of these shapes through the same recursive classification module bindings use, including destructured object patterns (a synthetic record parameter named by its pattern text), pure function types and `unknown` carried opaquely (writes to opaque-declared bindings erase to opaque, so mixed-kind rebinding joins soundly), and `Number.parseFloat`/`parseInt`/`Number` as honest possibly-NaN sources the `isFinite`/`isNaN` guards launder; a string's `.length` reads as a fresh nonnegative integer, and `instanceof` against a declaration-file name answers an unknown boolean; `let` and `const` bindings, locally and at the top level; `if`/`else`, `for` loops with a condition and an incrementor, `for...of` over arrays, `return`, blocks, expression statements; arithmetic with `+ - * / %` (the remainder reuses division's nonzero-requirement machinery and its guards), comparisons including `!==` and boolean equality (`flag === true` answers exactly) (both equality branches narrow — `if (count !== 0)` proves the true branch nonzero), ternaries, boolean `&& || !`, null checks (`x === null`, `x != null`, `typeof x === 'number'/'string'/'boolean'` where the type settles the answer — elsewhere typeof answers an unknown boolean and both branches analyze), `??`, optional chaining `a?.b` link by link (the mixed `a?.b.c` spelling stays out), and the `??=`/`||=`/`&&=` assignments; `switch` on a number, string, or possibly-missing string subject when every non-empty case body ends in `break`, `return`, or `throw` (no fallthrough — the owner-settled rule; stacked empty labels share the next body, `default` comes last, and a number subject gets the same `===` narrowing an if-chain would); string building with `+` and `+=` when the checker types the result as a string (the result is carried without claims, like a template literal); parameter defaults that are plain literals provably inside the assumed kind (`zoom: number = 5` is fine; `= Infinity` or `= readConfig()` rejects, since the analysis never evaluates the initializer); assignment to variables including compound forms and `++`/`--`; property reads, element reads (`arr[i]` honestly possibly-undefined, `arr[i]!` asserted), `.length`, and object spread (property writes are rejected — see the immutability rule below); calls to the file's own top-level functions, to `Math.floor`, `Math.min`, `Math.max`, `Math.abs`, and to `Number.isInteger` / `Number.isFinite` in guard position (both narrow). The tagged rejection reasons and their prose in `src/report` enumerate the boundary exactly, and growing the list is always a deliberate act — widening a strict rule later is cheap, while loosening-by-accident is what post-hoc reviews keep catching.

Values are immutable after construction (owner-locked, on trial): an object is written exactly once, by the literal that creates it, and property assignment does not exist in the subset. `config.pos = 1` is rejected. Rebuilding and rebinding with `config = {...config, pos: 1}` may be suitable for plain data when object identity, accessors, proxies, and the mutation itself are not observed. Variables stay mutable: locals and module `let` bindings rebind freely, so state lives as a tree of records hanging off module roots, updated by rebuilding the changed path and rebinding the root. Object spread is supported for exactly this idiom (one read per source property of the statically known shape, later entries override). The rule's reach: functions cannot mutate arguments or anything else, so a callee's whole effect is its return value plus module rebinds; two object parameters are fine (aliasing between them is unobservable without writes); and arrays, when they land, enter construction-only — no element assignment. The trust ceiling on module state was never about mutation (it comes from callback ordering), so nothing is lost at the roots, and everything below a root is exact.

The subset is prescriptive, not merely descriptive (owner-stated). The analyzed code is written by agents, and an agent can massage code into an analysis-friendly shape on request — so when a pattern is costly to analyze, the preferred move is to reject it and let the writer reshape the code, e.g. preferring immutable, freshly returned objects over in-place mutation, rather than growing the analyzer around semantics that existed as ergonomics for human writers. Aim for the shape of ordinary modern code, then aggressively simplify toward what makes the analysis easy. The demo file is a focus corpus, not a pattern specification: not everything it does is typical or desired, and supporting a construct merely because the demo uses it is never a goal by itself. Rejection prose names the construct and its location. The audit catalog contains conditional examples and behavior warnings when syntax provides enough evidence for useful guidance.

One narrowing assumption rides along with `in` checks: `'tab' in route` splits variants by their declared properties, which is sound only when values carry no properties beyond their declared type (width subtyping can smuggle extras in). TypeScript's own in-narrowing makes exactly the same assumption, and the no-dynamic-objects rule below fences it.

Optional properties (`session?: boolean`) are modeled as their maybe-undefined values: the declared kind wraps the property in the undefined sentinel, object literals fill omitted optionals with an explicit undefined (so a join between a branch that set the property and one that omitted it keeps it, and every read finds an honest value), and spreads copy them like any property. The representation deliberately combines absence and explicit undefined. Ordinary reads observe the same value either way; `'x' in obj` treats an optional property as unknown presence; and other presence-sensitive operations are outside the supported subset. This remains sound when the project disables `exactOptionalPropertyTypes`.

The subset also assumes the program runs without JavaScript's dynamic object machinery: no Proxy, no getters or setters, no Object.defineProperty, no prototype mutation, no custom valueOf or toString coercion, and no observer callbacks reacting to changes (callback ordering is punted regardless). Inside the analyzed file most of these cannot appear anyway — accessor properties and `new` expressions do not lower — so the assumption's real content is about values crossing the file boundary: a caller of an exported function is assumed to pass plain data objects, so a property read in a report means an ordinary read, not a Proxy trap that could answer differently each time. The assumption runs outward too: outside callers must not mutate records the module hands out — an exported record binding, or a record inside an exported function's return value. Analyzed code cannot mutate them (values are immutable in the subset), but a plain type-checked caller elsewhere could write a property through the escaped reference; the analyzer trusts that callers treat the module's records as the module does. This sits alongside the existing assumption that globals like `Math` are unmodified.

Once the check admits a function, the engine must be total over it: evaluation ends in a return value or a recorded stop, never a thrown error. A `throw` inside the engine states an invariant the acceptance check is supposed to guarantee, so reaching one from accepted source is a bug in the check, not a case for the engine to handle. This gives soundness reviews one boundary to attack instead of twenty scattered ones. One surface gets a softer rule (owner decision): TypeScript's narrowing is an open-ended set, so a value can reach an operation whose kind our narrowing did not establish even though the checker's did — e.g. a guard hidden in a ternary condition. That is a mismatch between two narrowing systems, not a gate bug; the engine records a per-path stop with its own reason (`narrows a value in a way the analysis does not model`) through one catch point, and reviews drive the residents of that bucket down. The catch uses the existing value-producer table to recognize one common case separately: a bare array read that is still possibly undefined when an operation needs a present value. That stop says the element may be missing and routes to the corresponding audit guide; it does not add provenance to the abstract value domain.

## What does the analyzer know about the browser platform?

Numeric facts about browser globals live in one catalog (`src/lower/platform.ts`), the analyzer's trusted base the way `lib.dom.d.ts` is the type system's. Each entry is a deliberate, written decision, because a wrong range poisons everything downstream — and the entries deliberately encode platform quirks rather than optimistic assumptions: no scroll-position entry claims nonnegativity, since Safari rubber-banding reports negative values at the edges. Current entries: element client sizes are nonnegative integers; window inner sizes are nonnegative but can be fractional under zoom; scroll positions are finite with no sign guarantee; `performance.now()` is nonnegative and fractional; `Date.now()` is a nonnegative integer.

A matched read produces a fresh value within the recorded range on every evaluation — platform state is mutable, so two reads of `clientWidth` may differ and are never assumed equal. Matching requires the root identifier to resolve into a declaration file, the same shadowing defense the `Math` dispatch uses. Only number-valued entries exist so far; `T | null` APIs are representable since nullability landed, they just have not earned catalog entries yet. The payoff composes with everything else: a function with no parameters at all, reading `document.documentElement.clientWidth` and clamping, gets a fully proven range like 1 through 7.

## What state survives when execution reaches unsupported code?

Keep information that was established before the unsupported operation, but mark the result as partial and record where and why analysis stopped. Partial information describes only the code that ran before the stop. It must not be used as a complete function postcondition or as the final program state.

For example, given `let width = 100; unsupportedOperation(); width = 200`, the report may say that `width` was `100` when analysis stopped. The report must not claim that the function returns with `width` equal to `100` or `200`.

What reports keep today is smaller than that example: the returns from paths that completed, and the requirements found along every path the analysis evaluated, including paths that later stopped (the `on analyzed paths:` lines). A stop record carries only its location and a tagged reason, so printing values at the stop — `width` being 100 above — is punted. When the unsupported construct is found during lowering rather than during evaluation, an ordinary function's whole half-built body is thrown away, keeping nothing. The module initializer is the exception: its lowering skips an unsupported top-level statement — recorded as a `skipped:` line on the module initialization entry — and keeps going, because real top-level code interleaves browser calls with the state initialization that is exactly the product the initializer exists to compute. Every binding a skipped statement could write is demoted, so nothing downstream trusts a value skipped code might have changed.

A called function that reaches unsupported code contributes nothing to its caller: the caller's path stops at the call site, and later caller statements on that path are not analyzed. Whatever the callee computed before its stop stays in the callee's own entry as `on analyzed paths:` evidence and never becomes the caller's state.

In reports, a partial function prints `stopped:` lines (where and why each path stopped), the module initialization entry additionally prints `skipped:` lines (top-level statements the lowering skipped), and both print `on analyzed paths:` lines (what the completed paths returned, and the requirements found along every analyzed path — evidence about the paths that ran, not a guarantee about the whole function). These evidence lines deliberately read differently from `requires:`/`ensures:` lines, and the partial report shape has no fields for those lines, so evidence cannot print as a guarantee.

Known report limits worth keeping in mind: mutually recursive functions currently blame each other — each entry says `calls <the other>, whose analysis stopped` — and neither names recursion (only direct recursion prints `recursive call to …`). Summaries distinguish `possibly NaN` (NaN reachable) from `possibly non-finite` (only overflow to infinity reachable); overflow of clean operands never claims NaN. A degraded line also names where the degradation was born, e.g. `(can overflow at demo/index.ts:41:22)` — carried by an annotation-only field on the abstract number that is deliberately excluded from state equality (participating would disturb loop fixed points) and never branched on by the engine, so blame is best-effort prose: joins keep one side's site, and a recovered value prints no suffix. Naming the unbounded input itself (rather than the operation) is a possible extension via the requirement-expression machinery. An unsatisfiable requirement renders verbatim, e.g. `requires: 0 is nonzero` for a literal division by zero — and the nonzero-divisor assumes fallback inherits the same policy when the divisor is provably zero at a call site (a review round confirmed the line is vacuous, never wrong; upgrading either to a definite division-by-zero diagnostic is counterexample-flavored reporting, a punted category). The CLI exits 0 whenever analysis ran, including reports full of unsupported and partial entries. TypeScript errors and genuine crashes exit nonzero; in project mode, source files without TypeScript errors still analyze.

## How should non-finite numbers be modeled?

Number parameters default to finite and non-NaN (object parameter properties get the same treatment). Numeric operations must prove that they preserve that property. If an operation may produce NaN or infinity, report the requirement needed to keep the result finite (division and remainder require a nonzero divisor; overflow adds no requirement). When the requirement cannot be named over the function's parameters — the divisor is a join (`??`, a ternary, a loop-carried variable), a module read, an element read, or a call result — the report keeps analyzing and prints an assumes line instead (`assumes: the divisor at <site> is nonzero`, the same channel asserted element reads use), computing the operation over the divisor's range with zero cut out. A violated assumption makes the downstream claims vacuous, like any assumes line. This replaced the earlier divisorUnknown stop, which lost everything downstream of the operation. Two exemptions: a division or remainder whose result is consumed only by comparisons needs no requirement and no stop (a NaN or Infinity result just makes the comparison true or false, which the boolean domain covers — `a / b > 5 ? 1 : 0` analyzes to an exact 0 through 1 with no requires line), and requirements can name `Math.floor(...)` over nameable operands, so `width / Math.floor(cols)` mints `requires: Math.floor(cols) is nonzero` and, the divisor being an integer of magnitude at least 1, ensures a finite quotient.

Ensures assume the requires (owner-locked): once a nonzero requirement is recorded for a divisor, the operation is computed over the divisor's range with zero cut out, so the entry reads as one contract — requires X, and given X, ensures Y. For division, an integer divisor then has magnitude at least 1 and the quotient is genuinely finite; a non-integer divisor can still sit arbitrarily close to zero, so its quotient honestly stays possibly non-finite (never NaN). A remainder with a nonzero divisor is bounded by its operands and stays NaN-free when the dividend is finite. Separately, for divisions and remainders whose results escape comparisons, the requirement is still created at the operation itself, without checking whether a zero divisor could actually affect the function's final result; the comparison-only exemption above is the first piece of deriving requirements from the final guarantee, and the general version remains the intended end state. Naming property paths in requirements, e.g. `requires: grid.columnCount is nonzero`, used to additionally need proof that the property is not written between function entry and the operation; with values immutable after construction, that proof is free, and only the requirement-language extension itself remains (punted).

The analyzer must still represent possible NaN and infinities internally, so it can explain where the possibility came from and pass requirements to callers. Addition and subtraction stay exact over possibly-infinite NaN-free operands — the only NaN case is opposite-signed infinities meeting, so `(a + b) + c` with finite inputs reports possibly non-finite, never NaN, while `(a + b) - (a + b)` honestly keeps the NaN possibility (both sides can overflow to the same infinity). Multiplication and division still collapse on possibly-infinite operands, where the NaN corners (`0 * Infinity`, `Infinity / Infinity`) are denser. Operations that make a value finite again are recognized where they are exact: `Math.min`, `Math.max`, `Math.floor`, and `Math.abs` keep their bounds even over possibly infinite inputs (no rounding, no overflow, no NaN creation), so `Math.max(0, Math.min(v * 2, 100))` ensures 0 through 100 even though the doubling can overflow. NaN is never recovered this way — `Math.min(NaN, 100)` is NaN — so the flag carries through, and a clamp cannot launder a possibly-NaN value into a clean range. Do not stop analysis merely because an intermediate result may be non-finite.

### Floats, not reals

The domain models IEEE doubles, not real numbers, and the difference is load-bearing, not pedantic. The deciding example came from production code: `jobWidth / jobHeight` with both operands guarded positive can still BE zero — `5e-324 / 2 === 0` by gradual underflow — so a later division by that ratio divides by zero on real hardware, while a reals-based analyzer would prove it safe. Same story in the other direction: `1e-200 * 1e-200 === 0` is why small constant factors never peel off requirements. Modeling reals would be simpler and more algebraic (associativity, exact division), and every one of those algebraic conveniences is a statement that is false on the machine.

What makes the float choice affordable is the prescriptive stance (owner decision): when float behavior blocks a proof, the answer is to rearrange the USER code, not to weaken the domain. Rearrangements that are equal over reals but differ in float rounding — `width / (jobWidth / jobHeight)` rewritten as `(width * jobHeight) / jobWidth` — are sanctioned by default, because ordinary layout code never aims at one specific rounding; the analyzer's float honesty is then the map of where to rearrange. The one exception to flag in reviews: code that deliberately manages float precision (the masonry column packer keeps exact running sums and floors only for comparison, per its own comments) — there, a rearrangement changes behavior someone chose, and the code comment marking the choice is the boundary.

## How are missing values modeled?

JavaScript has two missing-value sentinels, and they share one abstract concept: a value is a number/boolean/record, missing, or either (`{kind: 'nullish'}` and a `maybeNullish` wrapper). Each carries WHICH sentinels it can be — null, undefined, or both — so report prose says `animatedUntilTime is null or a finite non-NaN number` when only null is possible, and narrowing follows the runtime's actual rules: `x !== null` on a `number | undefined` value proves nothing about undefined (they are different values, and the check's else branch is unreachable — the analysis prunes it), while loose `x == null` clears both sentinels at once. `??` computes both possibilities: `animatedUntilTime ?? now` is the number or the fallback, exactly. The sentinels exist to keep number ranges flowing through ordinary "no value yet" code — null itself is never the interesting part of a report.

Missing-ness is the honest encoding, so the prescriptive rule runs the other way from mutation: a sentinel number (`-1` for "unset") pollutes the range and no checker verifies its specialness, while `number | null` keeps absence separate from the range and TypeScript enforces every check. The weird corners stay rejected instead: `??` across mismatched kinds, and unions mixing more than one non-missing kind. (Optional properties used to sit in this list; they model as maybe-undefined values now — see the acceptance section.)

## How are arrays represented?

The type system's own split, mirrored. A tuple type (`[4, 8, 24] as const`, tuple annotations) is positional: one value per slot, constant-index reads exact, provably in bounds. An array type is homogeneous: one element hull covering every element plus a length interval, uniform rules, no per-index claims. A tuple meeting a different-length tuple or an array at a join collapses one-way into the array form. The engine treats bare `arr[i]` as possibly undefined regardless of the project's `noUncheckedIndexedAccess` setting (`arr[i] ?? 0` analyzes with no assumption). If a possibly missing bare read reaches arithmetic, property access, or another operation that needs a present value, the path stops with `uses a possibly missing array element without handling undefined`; this remains honest in projects where TypeScript itself reports the element as present. `arr[i]!` asserts presence, and an unproven read becomes an assumption line through the same channel preconditions use — accumulated where the engine evaluates the read, adopted from completed callees at the call. `for...of` desugars to a counter loop whose element read is in bounds by construction, so array loops add no assumption noise, and an empty array's loop body prunes to nothing.

## How should module initialization be modeled?

Lower each module's top-level runtime code into a synthetic initializer function. Execute that function with the same CFG and evaluator used for ordinary functions. A small module setup phase still allocates module variables and exported bindings, initializes runtime dependencies first, ensures each module runs once, preserves side-effect-only imports, and shares live module bindings with later functions and callbacks. Function declarations do not run during initialization unless top-level code calls them.

For now, reject runtime import cycles and top-level `await`. Reject only the affected group of initialization dependencies; unrelated modules and self-contained function summaries remain analyzable. Type-only import cycles do not affect runtime initialization. Module slots must distinguish uninitialized values from initialized values so runtime cycle support can be added later without replacing the architecture.

What a function may assume about a module binding follows one rule, with no const/let special-casing: trust a value only when no write can happen between initialization and the function's call. Two kinds of bindings qualify: `const` bindings (reassignment is impossible, and with values immutable after construction, a const record's property values are as fixed as a const number), and any binding — const or let — that no code outside the initializer ever assigns, which a whole-file scan can check. The scan reads the entire file's text, bodies of rejected functions included, and any write-position form it does not recognize counts as a write — missing one would publish a stale value. A qualifying binding publishes its exact value, records included: `const gridSize = {cols: 8, rows: 6}` reads as that exact record inside every function, nested records to the leaves. Everything else contributes only its declared kind — some finite number, some boolean, or some record of the declared shape, e.g. a `pointer` record that a function rebinds reads as a record whose `x` and `y` are unknown finite numbers. A declared type maps through the same recursive classification parameters use — numbers, booleans, records, tuples, arrays, nullable wrappers, tagged unions, optional properties as maybe-undefined, and opaque leaves for the rest (function-typed properties, types the project did not write); only bindings whose whole type fails to classify stay uninitialized, and reads of those stop. An imported binding normally stops the same way — the other module's contents are invisible — with one carve-out: an import resolving to `export const NAME = <numeric literal>` in a project file reads as that exact constant (const cannot rebind, an import-cycle read before the declaration throws by TDZ rather than yielding a stale value, and a literal needs no cross-module analysis; anything beyond a literal keeps the stop). The declared kind is itself an assumption, not a guarantee: TypeScript accepts an `any`-typed value in any write position, so a type-checked write can still put a non-boolean in a boolean binding. The report therefore prints a condition for every declared-kind read — `assumes: scaleFactor is finite and not NaN` for numbers, `assumes: debug is a boolean` for booleans, and one line per leaf for records, e.g. `assumes: pointer.x is finite and not NaN` — and the line appears on every function whose result rests on the assumption, including callers of the reading function, since a callee evaluates on its caller's module state. A value with three or more number leaves folds the repeated number default into one line, e.g. `assumes: every number in pointer is finite and not NaN` (parameters fold the same way); the folded line covers every number leaf regardless of nesting, variant, or null wrapper, boolean leaves keep their own lines, and values with one or two number leaves keep the exact per-leaf lines.

`eval` needs no treatment here: the acceptance rules above put a file mentioning `eval` entirely outside the subset, so the write scan and the publish rule never see one.

A qualifying binding stays trustworthy even when top-level statements were skipped (owner-locked: whole-file publish). The soundness argument has two halves. Writes: every binding a skipped statement could write is demoted — its own declarators and assignment targets by a per-statement scan whose unrecognized forms count as writes, and writes inside functions it calls by the whole-file scan — so the binding itself cannot publish a stale value. Demotion alone is not enough, though: the initializer's own evaluation would keep the stale pre-skip slot value, and a later analyzed statement like `const doubled = scale * 2` would publish the laundered result through a fresh binding nothing demotes. So at each skip point, every binding the statement could write — its own targets plus, since it may call any function, every binding functions write — has its slot reset to the declared-kind unknown (untracked bindings to uninitialized), making later statements compute from covering values. Control flow: if a skipped statement throws or never returns at runtime, the module fails to finish loading, so no exported function can ever be called and every claim about them is vacuously true; ordering beyond that cannot matter because skipped statements' effects are already demoted. For analysis-time stops (a top-level call into a function that hits unsupported code), the CFG rule still applies: the binding must be initialized at every path end, and no write may sit at or after a stop or in a block still reachable from one — reachability on static edges, because a stop inside a loop can first appear on a late fixed-point round. This is built: the initializer runs first with every slot uninitialized, its per-path-end slot states are joined (a binding uninitialized on any end publishes nothing), and each declared function's slots are then seeded — published value, declared kind, or uninitialized (imports, objects, unsupported types; reading an uninitialized slot stops that path with the binding's category in the report prose). A loop whose exit is never taken on any analyzed path (e.g. `for (let index = 0; true; index += 1) {}`) also ends the initializer with a recorded stop on the loop rather than a crash, and everything written before the loop still publishes.

Two related assumptions are worth stating. Single-file analysis assumes no runtime import cycle brings a partner module in before this module's initializer runs; the assumption is unenforced, but with `var` outside the subset its teeth are gone — a cycle calling an exported function early makes the read of an uninitialized `let` or `const` throw, and a path that throws makes no claim wrong. And global objects like `Math` are assumed unmodified — the whole-file scan watches module bindings, not reassignments of globals.

With runtime cycles and asynchronous initialization excluded, module top-level execution consists of ordinary calls, branches, loops, heap operations, and unsupported-code handling. Reusing the normal evaluator avoids a separate module interpreter and duplicated semantics. Setting up module dependencies and live bindings is module-specific, but executing their code is not.

## How should callback ordering be modeled?

Do not model callback ordering for now. Analyze supported callback bodies independently, using ordinary function summaries and explicit assumptions about their parameters and available state. Registering a callback may still be reported as an effect, but registration does not cause Freerange to choose an execution order or execute the callback later.

Module initialization remains analyzable because it has a defined runtime dependency order. Callback summaries must not assume that mutable module state still has its initial value merely because initialization assigned that value earlier. The same holds for exported functions, which also run at arbitrary times after initialization.

This keeps general functions such as `render(state)` useful without knowing which events created `state`. It also avoids exploring many possible callback sequences. A caller-selected, bounded callback scenario can be reconsidered later if a concrete report needs stronger evidence that a state is reachable.

Keep purity analysis much smaller than old Freerange unless the current project demonstrates a concrete need. When purity work begins, both the primary agent and the agent implementing purity must read `spec/purity.md` on the `pre-pivot` branch — it documents the owner's pre-pivot decisions on the accepted purity subset clearly — and consult thread `019f0365-0939-7a50-a509-46c7733b455b` for the earlier semantic decisions and edge cases. Do not inspect or port that work before purity becomes the active task.

The old documentation and thread define an upper bound, not a feature list for the rewrite — and since everything there is pre-pivot, possibly none of it applies at all. If they say a purity feature was unsupported, the rewrite must not support it. If they say a feature was supported, that only makes the feature a candidate. Ask the user before including it. The owner has said explicitly that an even smaller subset than the pre-pivot one is acceptable, so prefer the smallest subset the post-pivot analysis actually needs, even when old Freerange implemented a broader rule.

## What do inferred requirements mean?

Every inferred requirement must say which guarantee it enables. A requirement does not mean that the program is otherwise invalid. For example, if a function divides `containerWidth` by `columnCount`, the report should explain what `columnCount` must satisfy to guarantee a finite, non-NaN return value.

Infer the requirement from the desired final guarantee, not from the operation alone. Do not report a requirement merely because an intermediate operation may produce a non-finite value; later code may make the result finite again. Restrictions needed only because Freerange does not support an operation should be reported as unsupported code, not as caller requirements.

Derive the full safe range rather than stopping at an obvious local condition. A nonzero divisor avoids division by zero, but finite inputs can still overflow during division. If `containerWidth` may be any finite number, `Math.abs(columnCount) >= 1` is a sufficient condition for a finite quotient. If the possible magnitude of `containerWidth` is smaller, the minimum safe divisor magnitude can also be smaller. Without a known sign, the safe values may be two ranges: `columnCount <= -minimumMagnitude` or `columnCount >= minimumMagnitude`. Earlier facts such as positivity or integrality should simplify that requirement, e.g. to `columnCount >= 1`.

The report should include the operation and source location that caused the requirement. At a call site, Freerange should prove the requirement, pass the unproven part on to the caller's own callers, or explain which guarantee can no longer be made.

Status: this section is the aspiration; what is built is the nonzero condition (no magnitude or overflow conditions, and the requires line names the operation, not the guarantee it enables). Guard discharge is real — `if (columnCount === 0) return 0` removes the requirement through the excluded-point cut. The gap between aspiration and built lives in the punt list (guarantee-driven derivation, expression growth limits).

## How are requirements derived and discharged?

The design in one sentence: a requirement is created at the operation that needs it, simplified only where the simplification is exactly true for floats, and removed when the ordinary forward analysis proves it satisfied — never by logical solving. Created at the operation: a division, remainder, or asserted element read records its own condition, expressed over parameters, constants, arithmetic, `Math.floor`, and property paths; nothing works backward through the surrounding arithmetic. Simplified only where exact: `(width - 4) is nonzero` becomes `width is not 4` because those two conditions are equivalent for every float, not approximately equal — a fact of IEEE gradual underflow (a subtraction whose exact result is tiny is computed exactly), checked mechanically in the test suite over subnormals and random bit patterns rather than trusted from memory of the standard. `total / (width - 4)` requires `width is not 4` (IEEE subtraction is zero exactly when the operands are equal); `total / (scale * 2)` requires `scale is nonzero` (a factor of magnitude at least 1 cannot underflow the product to zero, so the multiply peels and the chain continues); `total / (x * 1e-300)` stays as written (`1e-200 * 1e-200 === 0` — a small factor CAN underflow, so peeling it would lie), and division never peels for the same reason. The simplification terminates on its own — every step shrinks the expression — so there is no cap to tune. Conditions over two unknowns print as written: `total / (a + b)` requires `(a + b) is nonzero`, never "a is not -b" (an owner-confirmed cap; solving is where the pre-pivot analysis blew up).

A requirement is removed by the forward analysis proving it, never by implication checking. Three mechanisms: evaluation (a constant argument makes the divisor provably nonzero, so no requirement is created), interval narrowing from guards (`count > 0` refines the float bound to the adjacent representable double via bit stepping, so the divisor interval excludes zero exactly), and the excluded-point cut for the one hole no interval endpoint can express — `count !== 0`, `width !== 4`, or the matching `===` early exit with the point strictly inside the bounds. One point per value is the cap (a second guard replaces the cut, which only widens — sound). The cut is set only by branch refinement and kept at joins and widening only when both sides exclude the point (a sign-split join like `[-5, -2] ⊔ [2, 5]` also earns the zero cut, since neither side contains zero). Division consumes the zero cut, and three float-exact rules — the peel inversions run forward — turn a point cut into a zero cut so the guard a peeled requires line names actually discharges it: `width !== 4` flows through `width - 4` (an IEEE sum is zero only on exact negation), `scale !== 0` flows through `scale * 2` (a factor of magnitude at least 1 cannot underflow a nonzero product to zero). NaN stays honest throughout: NaN lands on the not-equal side (`NaN !== c` is true), so the not-equal refinement never clears mayBeNaN and never prunes a possibly-NaN branch.

Asserted element reads follow the same pattern. `data[i]!` that the engine cannot prove in bounds mints `requires: i is a valid data index` when both the index and the array are nameable over the caller's arguments, and falls back to the assumes line otherwise (module arrays, local literals). The condition means: an integer from 0 through `data.length - 1`. Three proofs discharge it: the for-of counter (in bounds by construction), the interval argument, and the one relational fact the analysis carries — `i < arr.length` recorded as an index/array pair when the guard compares against that exact array's length. The pair set is deliberately not a relational domain: one relation kind, no transitivity, no arithmetic over it; pairs intersect at joins. Parameter- and value-rooted pairs never invalidate (they name immutable values), but module-rooted pairs drop at module writes, havocs, and completed calls — rebinding the module root is the subset's one blessed update idiom, and a bounds check proven against the old array must not survive `data = [7]`. Integrality and the lower bound still come from the index's own interval, so the full defensive guard is `Number.isInteger(slot) && slot >= 0 && slot < sizes.length` — and `Number.isInteger` / `Number.isFinite` narrow accordingly (the passing branch of isInteger proves integer, finite, and NaN-free; the failing branch of isFinite prunes when the value was already provably finite). A range-only guard on a float-typed index honestly keeps the requirement: `sizes[1.5]` misses.

Requirements are path-insensitive by design (owner-confirmed): `if (flag) return a / b` requires `b` nonzero unconditionally. Over-requiring is conservative-sound — a caller satisfying every requires line makes every ensures line hold — and conditions attached to requirements are the alternatives explosion this project explicitly avoids. Requirement expressions cannot blow up either: naming a divisor expands its defining chain into a tree, and a value used twice expands twice (chained squaring doubles per level), so the walk charges each instruction expansion against the function's own instruction count — a requirement can never be more complex than the function that produced it, by construction rather than by a magic number. Exhaustion surfaces as the same nonzero-divisor assumes line an unnameable divisor gets.

## How are objects represented?

An object is a plain structural value: a record carrying its property values directly, nothing else. Values are immutable after construction (see the acceptance section), so a record held across any amount of control flow — a loop rebuilding state each iteration, a helper called again, a branch merge — keeps exactly the property values it was built with. There is no abstract heap, no allocation identity, and no aliasing question; the earlier design (site-plus-call-site allocation identities with known/summary slots and displacement) was deleted once immutability made identity unobservable.

Records join pointwise by property name, keeping only the names present on both sides. Different shapes genuinely meet at joins: TypeScript's width subtyping types `flag ? {x: 1} : {x: 2, y: 3}` as `{x: number}`, and keeping the union of names would let the report claim something about a property that is sometimes absent. Widening recurses into record properties, since the numbers inside a record are the unbounded part; a loop carrying `metrics = {height: metrics.height + 1}` widens `height` at the loop header exactly like a scalar.

One expressiveness cost is accepted knowingly: two separately constructed records with equal property values are indistinguishable, so "definitely different objects" cannot be stated. Nothing observes object identity today — `===` never lowers for objects — and if object comparison ever enters the subset, the representation is the thing to revisit.

## How should loops be analyzed?

Do not unroll loops. Analyze the loop CFG until its abstract state stabilizes, then use supported recurrence or collection summaries. For example, one unconditional push per input can prove `output.length === input.length` without examining every item.

Unrolling makes analysis depend on runtime collection length and still cannot prove iterations beyond an arbitrary cutoff. If fixed-point analysis does not stabilize and no supported summary applies, report the property as unresolved.

The convergence limit counts fixed-point rounds of one loop header's abstract state, not runtime iterations. Widening makes ordinary counting loops converge in two or three rounds regardless of how many times the loop runs at runtime; the limit exists only to guarantee termination when each round genuinely keeps changing the state. The only known way to hit the limit is a chain of loop-carried variables longer than the limit (widening settles one variable per round). Records do not prevent convergence: a loop-carried record widens pointwise into its properties at the header, exactly like a scalar.

When any path inside a loop stops, the loop header cannot reach its fixed point, and a stop can first appear on a late widening round after earlier rounds already propagated returns downstream. Returns reachable from such a header are therefore not evidence and are suppressed; returns before or bypassing the loop survive. This deliberately also suppresses evidence from the path where the loop body runs zero times, when the stop existed from the first round.

**warn:** summary discovery needs explicit limits before implementation; the fixed-point limit already exists (16 rounds per loop header).

## How are results reported?

Project and file commands expose different amounts of the same analysis. Bare `fr` prints unresolved caller contracts and the two stops that are findings in their own right: `out-of-bounds-read` is an error and `non-exiting-loop` is a warning. Each finding uses the conventional `file:line:column level message [rule]` shape, followed by honest project coverage. `fr <file>` prints that file's complete per-function contracts, including ranges, requirements, assumptions, and partial or unsupported functions. A linter can only speak about findings, so a refactor that silently weakens a derived guarantee, e.g. an "at least 54" line disappearing, is visible only by inspecting or deliberately snapshotting the exact contract output.

Bare `fr --audit` prints a compact project index of locations where the refactoring catalog has applicable guidance, plus project coverage. `fr --audit <file>` prints coverage before that file's contracts and says plainly when only part of the file was understood. It then selects a small set of refactoring examples from structured requirements, assumptions, stops, and lowering reasons. Selection is intentionally sparse: when syntax alone cannot determine a safe rewrite, the audit gives no recommendation. The audit prints one primary example for each cause and describes secondary options without repeating their code. Every displayed snippet is analyzed in the test suite, and examples that may change behavior also have runtime tests for the stated difference. Neither command edits source code or writes report artifacts.

## Additional decisions

- Analysis runs forward, creates requirements at operations, passes unproven requirements to callers, and reports inferred guarantees.
- Each CFG block keeps one merged abstract state. We do not retain every path.
- Block parameters carry values across branches and loops.
- Branch refinement stays at pattern-matching depth (owner-stated wariness of anything deeper): a branch on a single comparison narrows that comparison's two direct operands, a branch on a single null check narrows the checked value (consulting which sentinels it can be), and nothing else — no back-propagation through arithmetic (`x * 2 > 4` does not narrow `x`), no relational facts. Compound `if` conditions narrow without deeper refinement because LOWERING splits them: statement-position `&& || !` become short-circuit CFG, so `if (x !== null && x > 0)` is two chained single-check branches — the same shape as nested guards. Ternary conditions route through the same splitting, so `a > 0 && b > 0 ? a / b : 0` refines each conjunct in its arms exactly like the if-statement spelling; a compound guard stored in a boolean first (`const ok = a > 0 && b > 0; ok ? ...`) still does not narrow — narrowing through stored predicate values stays out. A null check on a property read narrows through the producer chain into the record (sound because values are immutable). Anything deeper than this needs explicit owner sign-off — the two soundness bugs in the refinement machinery to date (the NaN branch prune, and the false branch refining despite a possibly-NaN operand) both lived exactly on this surface.
- Caps must fail closed, and each one states which failure it buys. The fixed-point limit is 16 rounds per loop header; hitting it records a stop, never a wrong fixed point. Type walks stop at depth 8; the `seen` set already handles ordinary cycles, while the depth limit handles recursive generics whose levels are fresh checker types. A cut rejects the type or degrades a record property to a claim-free opaque leaf. Requirement-expression expansion gets at most one instruction visit per instruction in the function; exhaustion prints the nonzero-divisor assumption instead of inventing a caller requirement. An abstract number retains at most one excluded point; another exclusion can discard precision but cannot strengthen a claim. No cap may silently strengthen a result. TypeScript's checker bounds type instantiation too, so an uncapped type walk could not reliably terminate on every accepted input.
- The repeated adoption pattern for component code is to move numeric layout work into a plain top-level `.ts` function and let the component consume the returned numbers or record. The coachmark, virtualized grid, masonry card heights, and page frames all became analyzable this way while hooks, DOM calls, and rendering stayed in their components.
- Browser behavior comes from static models. No browser probes.
- Reports distinguish input assumptions (`assumes:`), guarantees (`ensures:`), inferred requirements (`requires:`), unsupported code (`unsupported:`), and partial results (`stopped:` plus `on analyzed paths:`). The README and file-audit introduction explain those terms to a reader seeing Freerange for the first time. Rejection lines may include a short conditional hint, but full examples and behavior warnings stay in the audit catalog so report prose does not imply that a syntax rewrite is always safe.
- Four bounded memo tables remain around recursive type classification: `declaredKind` and `valueKind` use the checker's interned type identity plus the remaining depth budget, `nonMissingUnionMembers` uses the interned union type, and `taggedUnionProperty` uses the stable member array plus depth. These are the engineering guide's sanctioned cache shape: checker types are immutable for the program's life, the tables contain at most one entry per distinct input, and no invalidation is needed. Independent gallery measurements justified every table: removing `valueKind`, `nonMissingUnionMembers`, or `taggedUnionProperty` made lowering 45–80% slower, while removing `declaredKind` made one difficult file more than five times slower. Types surface only as expressions are lowered, so the table is also the single upstream computation rather than a copy of another result. The former recursive comparison of untagged structural-union shapes was removed entirely instead of retaining its cache: the feature had no successful gallery use, slowed lowering by about 9% in a five-run median, and required about 100 lines of recursive machinery. Untagged structural unions now reject even when separately declared members happen to have identical shapes; use one shared record type or add a string or boolean tag.
- Stable numeric IDs identify functions, blocks, values, and source locations. Module and effect IDs will follow when effects exist.
- Module variables, heap objects, local values, and platform state have different lifetimes and should not be stored in one generic map.
- We use one lowering pipeline and one evaluator, rather than separate evaluators for module initialization, functions, and callbacks.

## Punted

- Source annotations. Analysis remains annotation-free for now. Reconsider annotations only when a report can explain that one would avoid substantial analysis growth or unlock a useful guarantee.
- Concrete counterexample search and replay.
- Deriving requirements from whether the final result is affected, with ensures lines that hold when the requirements are satisfied. Requirements are currently created at the causing operation, so a division or remainder whose bad result never reaches the return value still reports one; the comparison-only exemption in the non-finite section is the lone piece built.
- Printing values at a stop (`width` was 100), and recovering the loop evidence that gets suppressed when a stop happens inside a loop.
- Callback ordering and execution of callback sequences, including caller-selected bounded callback scenarios.
- The exact relational numeric domain and recurrence analysis.
- Modeling caught exceptions. `throw` is supported as a path terminator (a thrown path contributes nothing, which is exact while the subset has no `catch` — guard clauses like `if (bad) throw new Error(...)` discharge obligations, and a function annotated `: never` that throws on every path analyzes with callers treating the call like an inline throw). `try`/`catch` itself stays out; supporting it means real exception-flow modeling.
- Reporting every unsupported construct in a function instead of only the first.
- Naming a tuple position in a requirement: `pair[0] / pair[1]` on a `[number, number]` parameter falls back to the nonzero-divisor assumes line instead of minting `requires: pair[1] is nonzero`, because the requirement expression language has property paths but no element form. The assumes prose already names positions (`pair[1] is finite and not NaN`), so the language gap is the only missing piece. A guard on a local copy works in the meantime: `const divisor = pair[1]; if (divisor !== 0) { ... / divisor }` discharges like any other divisor guard. The direct `if (pair[1] !== 0)` spelling does not — each element read is fresh. (Module re-reads used to behave the same way, but a check on a module read now narrows the slot itself, so `if (divisor !== 0) { ... / divisor }` on a module binding discharges directly.)
- Naming a ??-defaulted value in a requirement: `const actual = divisor ?? 4; total / actual` falls back to the nonzero-divisor assumes line, because the ?? result is a branch-join value the expression language cannot see through (it has no fallback form and no view into block parameters). The guard-then-divide spelling (`if (divisor !== null) total / divisor`) mints its requirement fine.
- Forward propagation of narrowing into already-built copies: `const copy = {...grid}` then `if (grid.columns >= 1)` leaves copy.columns wide (the reverse — guarding the copy narrows the original — works). Reaching earlier-built records needs an occurrence index, beyond pattern-matching depth; guard before copying.
- Record and tuple parameters beyond the recursive declared kinds, `.map`/`.push`/array spread/holes, and narrowing through stored compound predicates (`const ok = a > 0 && b > 0; if (ok)` — the stored value is a branch join, not a comparison). A stored single comparison, e.g. `const ok = count > 0; if (ok)`, does narrow: the branch condition resolves to the comparison instruction that produced it, so a divisor guarded this way discharges its requirement. A simple dense-array aggregation may be rewritten as an explicit loop, but `.map` and other callbacks have observable behavior that syntax alone does not replace safely.
- Properties whose declared type mixes kinds, e.g. `{x: number | boolean}` written with a number on one path and a boolean on another. The join drops such a property (it is unreadable through the gates anyway); claims about the rest of the record survive.
- In-place object mutation. What was supported: property writes on locals and parameters with strong updates on single known objects and weak (joining) updates on branch-merged or summary targets; parameter writes printed as ensures lines. Restoring it is no longer additive (owner-approved trade): with records now plain structural values, the abstract heap, allocation identities, and displacement machinery were deleted outright, so mutation support means rebuilding an identity layer, not re-adding an instruction. The cheap middle if only local building chafes: mutation of provably unaliased, non-escaping locals lowers to per-field rebinding (~80 lines of escape checking) without any heap.
- Exact structural publishing in partially analyzed files. Today any unlowered function or skipped statement in the file demotes every module record, tuple, and array binding — nullish-wrapped ones like `number[] | null` included — to its declared-shape hedge, because unanalyzed code can mutate a structure through an alias the write scan cannot see (e.g. `Object.assign(config, ...)` hides the binding in argument position, `queue?.push(x)` in receiver position). Finer precision — demoting only bindings whose identifier or alias reaches unanalyzed code — is a possible refinement.
- Runtime import cycles and top-level `await`.
- Termination proofs and `decreases` clauses.
- The general method for discovering loop invariants.
- The representation and growth limits for symbolic arithmetic, branch conditions, and requirements with alternatives.
- Final widening, fixed-point, recursion, and function-summary caching policies.
- Purity features beyond the small subset that the post-pivot analysis eventually demonstrates a need for.
